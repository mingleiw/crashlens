Title

The Software Factory: What's Real and What I'd Actually Build

Article

Issue #2 of a series where I read the popular pitches, build guides, and rebuttals on a topic, check what holds up, and keep only what's worth using. This one: the software factory.

My coding agent missed two race conditions. Model checking caught them.

That shapes how I read every software factory pitch. Show me the code getting produced, sure. Then show me what catches a wrong answer before it ships.

I went through the funding announcements, the overnight build recipes, and the arguments over whether "software factory" means anything at all.

There are real products here and useful engineering ideas. There are also claims that go well past the evidence attached to them.

Here's what I'd keep.

First, separate the company from the concept

"Software factory" gets used for three different things.

The company. Factory sells coding agents called Droids. Its September announcement confirmed a $200 million raise at a $5 billion valuation and reported hundreds of thousands of developers on the platform. (factory.com)

The platform pitch. A computer that produces software on demand. Microsoft's local coding model is a real piece of that story. Its documentation describes free local inference alongside cloud models, with more than 120GB of RAM recommended for best performance. That's a much narrower proposition than an "infinite software factory" on every desk. (microsoft.ai)

The workflow. What engineers can build themselves: take a task, give an agent an isolated workspace, run checks, and decide whether the result can merge.

These overlap, but evidence for one doesn't prove the others. A funding round tells me someone financed a company. A local model tells me where inference happens. Neither tells me whether an unattended workflow reliably ships useful changes.

There is evidence. Check what it measures.

Factory publishes customer results. Its Nav case study reports feature development cycles twice as fast and less context switching. Those are relevant claims, and calling them "no evidence" would be unfair. (factory.com)

But a vendor-published customer story leaves questions open:

  • Which tasks improved?
  • How was the baseline measured?
  • How much human work remained?
  • Did defects go up?
  • Did the gains last beyond the initial rollout?

Those details decide whether the result applies to my team.

The same standard applies to DIY builds. A detailed recipe can be worth trying without proving it delivers working products overnight. A screenshot of a finished interface shows something. It doesn't show operating cost, reliability, or how much cleanup happened afterward.

I separate three claims:

  • It exists: there's a system or product someone can inspect.
  • It helped: there's a reported improvement on a defined task.
  • It works reliably: repeated runs, with the failures, costs, and human intervention counted.

The debate slides between these three far too easily.

StrongDM gets to the interesting problem

StrongDM's approach is deliberately aggressive: humans don't write or review the generated code.

That sounds like removing the checks. Their write-up describes a lot of work building different ones:

  • Agents took shortcuts to pass tests, so they store test scenarios outside the codebase, partly so tests can't be rewritten to match the implementation.
  • They built behavioral replicas of services like Okta and Slack, so agents can be evaluated across many scenarios.
  • Some evaluation uses LLM judgment instead of a simple pass/fail assertion.

They've also shipped software, including CXDB, an open-source context store for agents. That's more than a blog post about an imaginary pipeline. (factory.strongdm.ai)

The open questions are about the checks themselves: how well the scenarios cover real use, how faithfully the replicas behave, and how often the evaluator accepts a bad result.

Those are the questions I'd spend my time on.

The failure I care about

A factory can keep running while its definition of "working" drifts.

The agent implements the wrong behavior. A test checks the same wrong assumption. Everything passes. The next task starts.

Adding another agent doesn't fix this. Two agents can agree on the same wrong reading.

Making a check deterministic doesn't fix it either. A test can reliably assert the wrong thing.

My race-condition example matters because a different kind of check caught what the coding agent missed. Model checking has limits too: TLC checks a TLA+ model, and you still have to show that the model matches the implementation. (lamport.azurewebsites.net)

The lesson I take from that run is practical: give the workflow a way to prove its own answer wrong.

What I'd actually build

I'd start with one repository and a narrow class of changes whose behavior I can test.

1. Define success before anyone writes code.

Write down the expected behavior, constraints, and failure cases, and review them before the agent starts. If they need to change later, that's an explicit decision, not a quiet edit.

2. Give the builder an isolated workspace.

The agent gets a branch or worktree and the tools the task needs. Its permissions shouldn't let it bypass merge rules or quietly weaken the acceptance checks.

Markdown instructions can explain the rules. Permissions and CI have to enforce them.

3. Check behavior and keep the evidence.

Run the relevant tests, static checks, and end-to-end scenarios, and attach the actual results to the change.

An agent saying "all tests passed" is a report. I want the output from the tests that ran.

4. Test the checks.

Introduce a known-bad change and confirm the gate rejects it.

If the workflow claims to prevent duplicate processing, trigger duplicate processing on purpose. If it claims to preserve permissions, try an operation that should be denied.

Watching the gate reject a realistic failure tells me more than another successful demo.

5. Keep merge approval while you measure.

At first, the agent produces a reviewed proposal. I'd consider automatic merging only for narrow categories of change, after collecting evidence that the checks work.

Failed checks, changed acceptance criteria, and exhausted retry budgets go back to a human.

The numbers I'd want

For a defined set of tasks, I'd track:

  • Accepted changes out of all attempted tasks.
  • Human minutes spent reviewing and repairing them.
  • Total cost per accepted change, including failed attempts.
  • Defects found after merge.
  • Changes that needed a rollback.

Then compare them with the previous workflow on comparable work.

A system that produces more code while increasing repair work hasn't shown a productivity gain. A system that reliably removes tedious work can be valuable without building a whole product overnight.

The rule

I'd happily use the useful parts: isolated execution, clear acceptance criteria, protected checks, and evidence attached to every change.

Before I let it merge while I sleep, I want to watch it stop something that should never ship.
